# Bounded hierarchical rendering and selection-authored masks across the full stack

The follow-up closes the seven prior group/mask findings: wide-tree rendering now has a checked aggregate budget, Agent hierarchy proposals enforce destination depth, selection coverage can author masks through production QML, and raster actions share one projected capability. Hierarchy boundaries are explicit, pass-through remains honestly unsupported, and mutation routes converge on the transactional core command path. Core, Agent, FFI, and native smoke coverage exercises exact limits, transactions, projection, and UI capability state. **Watch for: confirmed, low severity — architecture and compatibility still claim Agent batches are committed as one grouped history entry, but production Apply commits each queued proposal independently.**

**Verdict**: NEEDS_CHANGES

## High-level view

Rendering preflights visible work as full-canvas operations before allocating output or group intermediates. The exported 256 Mi-pixel-visit boundary includes output initialization, each raster composite, and each group’s clear/composite pair; exact-boundary and first-over valid wide trees exercise the intended inequality.

Agent proposal validation derives destination depth and moved-subtree height from the validated hierarchy facts used for IDs, parents, cycles, and sibling bounds. Exact-depth add/move cases pass, while one-over destinations are rejected before inert proposals are produced.

`RasterMaskFromSelection` copies active full-canvas selection coverage into a new or existing enabled raster/group mask through one typed command. Agent conversion, C ABI execution, Qt forwarding, production QML invocation, render projection, disabled-mask state, and undo are covered without a side mutation path.

Qt projects `can_edit_raster`, sibling count, and top/bottom state from FFI summaries. Raster tools, pointer gestures, transforms, filters, and clear share the active-node capability; hierarchy movement uses bounded `MoveNode` controls and the root-only reorder control is no longer exposed.

QML and approved proposals enter `redrob_editor_execute_json`, which publishes only a validated cloned document through `Editor::execute`. Live Agent requests return inert, generation-bound proposals and require explicit per-proposal Apply, but **confirmed, low severity:** the architecture and compatibility matrix describe grouped Agent commit behavior that this production path does not implement.

## Aggregate render work is checked before full-canvas allocation

`Renderer::render_work_operations` uses the render traversal’s visibility, opacity, kind, and child relationships. It assigns one operation per raster, two per isolated group, and one to output initialization, then multiplies by checked canvas pixels and rejects values above `MAX_RENDER_PIXEL_VISITS` before output or intermediate allocation (`crates/redrob-core/src/render.rs:28-86, 159-187`). The count matches the full-canvas loops, including each group’s mask/opacity/blend composite at its parent boundary.

The 1,024² regression builds 127 visible root groups around the initial raster, landing at 256 operations and 256 Mi pixel visits, then proves a 128th group returns `RenderWorkLimitExceeded` (`crates/redrob-core/tests/editor_core.rs:1622-1652`). A separate depth test retains a valid depth-256 render, so work and hierarchy limits remain distinct.

## Destination depth includes the complete moved subtree

`ProposalContext` computes prospective depth from the destination parent and derives subtree height by tracing descendants to the moved root. `add_group` validates height zero; `move_node` rejects missing IDs and cycles before checking `destination_depth + subtree_height <= MAX_HIERARCHY_DEPTH` (`crates/redrob-ffi/src/graphics_tools.rs:1022-1048, 1594-1667`). Core repeats hierarchy validation transactionally at apply.

The proposal regression constructs a depth-256 chain and a two-level movable subtree. It accepts add, leaf-move, and subtree-move destinations exactly at the limit and rejects both add and subtree-move one-over cases (`graphics_tools.rs:3129-3227`). Same-parent core movement separately covers exact top, exact bottom, and the first invalid post-removal index.

## Selection coverage reaches raster and group masks through one command

Core rejects inactive selection without state change, preflights storage when attaching a mask, snapshots full-canvas 8-bit coverage, and installs an enabled `RasterMask` (`crates/redrob-core/src/document.rs:938-963`; `crates/redrob-core/tests/editor_core.rs:1990-2052`). The regression covers attach, overwrite, re-enable, render effect, and undo.

Agent conversion emits `Command::RasterMaskFromSelection` only for an existing mask-capable node with active selection (`crates/redrob-ffi/src/graphics_tools.rs:176-181, 1692-1706`). The ABI test creates a group, moves a raster child, selects one pixel, executes the JSON command, and verifies capability summary plus masked render (`crates/redrob-ffi/tests/ffi_api.rs:748-839`). Native smoke invokes the production QML `maskNodeFromSelection` function, checks mask/output projection, toggles the mask, and restores state through undo (`native/qt/main.cpp:59-126`).

## Shared raster capability and sibling boundaries drive QML state

FFI marks only raster nodes as `can_edit_raster` and reports `supports_pass_through: false`; `LayerModel` projects that capability with bottom-to-top sibling indices/counts before reversing rows for display (`crates/redrob-ffi/src/abi.rs:179-203`; `native/qt/LayerModel.cpp:60-102`). QML binds raster tools, pointer admission, transforms, filters, and clear to `editor.activeNodeCanEditRaster` (`qml/Main.qml:232-277, 356-396, 1005-1351`). Native smoke finds those production objects and verifies all are disabled for a group and enabled for a raster (`native/qt/main.cpp:27-57, 77-125`).

Sibling roles derive top from `siblingIndex + 1 == siblingCount` and bottom from index zero. QML disables the corresponding `MoveNode` actions at those boundaries and has no remaining `reorderLayer` caller (`native/qt/LayerModel.cpp:34-38`; `qml/Main.qml:596-607`).

## Isolated groups apply mask, opacity, and blend once

Each visible group renders children into one transparent intermediate and applies its enabled mask, opacity, and blend mode once while compositing that intermediate into its parent (`crates/redrob-core/src/render.rs:98-137`). Core assertions distinguish enabled/disabled masks, half-opacity isolation, multiply at the group boundary, and invisible-ancestor skipping (`crates/redrob-core/tests/editor_core.rs:1884-1987`). No command or serialized state introduces pass-through; ABI capability is false, architecture calls it unsupported in v2, and compatibility tracks it separately as planned.

## Production Apply is explicit, but grouped-commit documentation overstates behavior

QML mutations and proposal application converge on `EditorBridge::executeCommand`, `redrob_editor_execute_json`, `Editor::execute`, and `CommandBus::apply`. Core mutates and validates a cloned candidate before advancing generation, publishing state, and recording history (`native/qt/EditorBridge.cpp:360-401`; `crates/redrob-ffi/src/abi.rs:509-533`; `crates/redrob-core/src/editor.rs:433-469`). `redrob_agent_propose` only snapshots state; queued proposals retain generation/document epoch, and `applyProposal` rejects stale entries before applying one selected action (`crates/redrob-ffi/src/abi.rs:443-505`; `native/qt/EditorBridge.cpp:1364-1400`).

**Confirmed, low severity:** `docs/architecture.md:17` says “Agent batches are previewed and committed as one history group,” and `docs/compatibility.md:24` marks “preview, approval, grouped commit” native. The UI queues returned proposals separately, `applyProposal` executes one command/undo/redo, and no Agent path calls core’s `begin_group`/`end_group`. Describe generation-bound per-proposal Apply and separate history entries, or add atomic batch approval using core grouping with rollback and stale-generation tests.
