# Transactional proposal and FFI boundary hardening

The implementation hardens streamed completion accumulation, one-shot proposal generation, proposal validation, brush/ABI input handling, and selection snapshot ownership across `redrob-agent`, `redrob-core`, and `redrob-ffi`. Stream fragments are accumulated transactionally, proposal requests receive immutable document context without being offered inspection, and stale proposals remain gated by generation/document epoch before native application. Layer/history proposal validation retains core-side enforcement, and FFI snapshots remain independently owned. One blocking work-bound gap remains in brush execution despite the new point-count limit.

**Watch for:** **confirmed** — brush size and total raster work remain unbounded, so a schema-valid command can make the editor traverse a large canvas thousands of times.

**Verdict**: NEEDS_CHANGES

## High-level view

Completion accumulation checks call count, per-field bytes, per-call argument bytes, and aggregate argument bytes before inserting or appending any fragment. Sparse indices and interleaved calls remain independent, and rejected multi-field events leave both call state and aggregate counters unchanged.

One-shot proposal requests embed document/layer facts in the system prompt and expose only mutating proposal tools, so inspection is absent from the provider-visible contract. `ProposalContext` snapshots generation, layer IDs, and undo/redo availability; the same typed validation path feeds inert proposals and direct tool execution, while native application rejects stale generations and core execution remains authoritative.

The brush point count is consistently capped at 4,096 in the public constant, tool schema, proposal decoder, and core command path, and command JSON is capped at 1 MiB before deserialization. **Confirmed:** the brush schema and core only require a finite positive size, while raster work loops over every covered pixel for every dab; 4,096 repeated points with a canvas-sized brush can produce billions of pixel visits. Add a deterministic total raster-work budget enforced by core and reflected in the tool schema and native input path.

Selection snapshots clone the mask under the editor lock into a Rust-owned allocation with dimensions, stride, generation, and active state. Buffer and snapshot outputs reset before failure, and compiled C/C++ layout tests cover the allocator-return contract and snapshot survival across later edits.

<details><summary>Details</summary>

## Streamed completion limits commit whole events or nothing

`ChatAccumulator::apply` computes prospective ID, name, per-call argument, and aggregate argument sizes before calling `entry` or appending strings. This ordering means an aggregate-limit failure cannot attach an ID/name fragment, and a rejected sparse index cannot consume a call slot. Tests cover exact boundaries, fragmented IDs/names, sparse indices including `usize::MAX`, interleaved aggregate accounting, and rejected multi-field deltas.

## One-shot proposals use immutable context instead of an inspection round

`run_agent_proposal` snapshots document facts, layers, and `ProposalContext` under the editor lock, then releases the lock before the network call. The request embeds that snapshot in the system prompt and uses `proposal_tool_declarations`, which filters out `inspect_document`; the one-shot contract therefore does not offer a tool whose result would require another provider round.

Provider calls become inert `ProposalDto` values tied to the snapshot generation. The native queue also records a document epoch, preventing a document replacement at generation zero from reviving an old proposal; applying one proposal makes sibling proposals from the same response stale.

## ProposalContext narrows proposals without replacing core validation

Layer-targeting tools reject identifiers absent from the snapshot, add-layer indices are checked against the snapshot layer count, and undo/redo are rejected when their corresponding history capability is absent. Direct `GraphicsToolExecutor` calls use the same decoder before calling `Editor::execute`, `undo`, or `redo`, and core command execution commits document state, generation, and history only after command and aggregate validation succeed.

## Brush point bounds do not bound raster work

The point-count contract is aligned: `MAX_BRUSH_POINTS` is 4,096, the schema publishes that value as `maxItems`, proposal decoding rejects one over, and core rejects zero or one over without advancing generation. The ABI's 1 MiB command JSON ceiling is also documented in the C header and checked before deserialization.

**Confirmed:** brush `size` has only `exclusiveMinimum: 0` in the schema (`crates/redrob-ffi/src/graphics_tools.rs:181`) and only a finite-positive check in proposal/core validation (`graphics_tools.rs:975`, `crates/redrob-core/src/document.rs:533`). Core caps generated dab count, but each accepted dab scans its covered rectangle (`document.rs:558-581`). On the default 1280×800 canvas, 4,096 coincident points with a canvas-sized brush can exceed four billion pixel iterations. Enforce a deterministic total-work budget before rasterization and expose compatible limits in the tool schema and native stroke collection.

</details>
